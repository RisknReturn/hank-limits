# Mutation testing v0.2: the v0.3 checks on independently generated errors

Measured on branch `v0_3` (no tag, no release; the version, tags and citation metadata are those of v0.2.1). Plan, checks and predictions: `docs/CHECKS_PLAN_v0_3.md`, committed and pushed as P (`fc5cd27`) before any v0.3 check code was written and before any mutant was run; thresholds committed as T (`96b7fd9`) before any mutant was run. Runner: `scripts/mutation_v0_2.py`. Data: `out/mutation_v0_2.json` (every run's test outcomes and check summaries), `out/mutation_v0_2.csv` (one row per design × mutant × group).

`v0_3` was started from `mutation-v0_1` (`aa85365`), because PR #1 had not been merged; its model and test trees are those of tag `v0.2.1`.

## 1. Summary

- **Setup.** Two suites: v0.2.1 (the released tests, tag `v0.2.1`) and v0.3 (the same tests plus the new checks V1–V6, commit T). 20 new mutants and 3 controls, generated by a separate agent that saw the model code and the v0.1 mutant list but not the tests, the v0.1 report or the new checks (plan, section 6 and appendix A). Each mutant was applied to a copy of the model side (`models.py`, `core.py`) of each suite, and that suite's full pytest run was compared with its own unmutated baseline. 78 runs in all: (i) v0.2 mutants × v0.2.1, (ii) v0.2 mutants × v0.3, (iii) the 28 v0.1 runs × v0.3, plus two baselines per suite.
- **The fair comparison, (i) against (ii):** the v0.2.1 suite caught **14 of 20** mutants, the v0.3 suite **19 of 20**. The five gained are all caught by the new checks alone: N04 (real-rate rule on Y_{t−1}), N05 (countercyclical incidence that does not preserve aggregate income), N07 (quarterly r = 0.005 in the annual fiscal model), N10 (step size dropped from the GE options, which affects only T3) and N18 (wrong sign of the TANK saver asset target). Both suites missed N20, an error in a diagnostic (the constrained share) that no test asserts tightly.
- **The old groups behave the same.** In every one of the 23 runs, groups T1–T6 and D gave the same verdict in the v0.3 suite as in the v0.2.1 suite (T6: the split Ricardian test fails where the composite one did). In design (iii) they reproduced the v0.1 verdicts of all 28 runs exactly. On the unmodified code, all 276 numbers of the v0.1 check summaries are bit-identical to v0.1 run B0 in all four baseline runs.
- **Controls:** no false alarm in either suite (K01–K03). Among the v0.1 controls, C03 (T3 goods-market target) alarms in V1 in the v0.3 suite, as pre-registered: its asset-market residual is large because of F3. The threshold was not adjusted.
- **Pre-registered predictions:** in (i), 145 firm group-level predictions, 144 held; in (ii), 168, 167 held. The one failure is the same cell in both: N13 was predicted to pass T2 and failed it (section 7). Suite level: 12 caught predicted for v0.2.1 (14 observed: N13, and N01 via an "unsure" T4 cell); 18 for v0.3 (19 observed: N01). All 23 group-V predictions (20 mutants, 3 controls) held.
- **v0.1 mutants (iii):** the v0.3 suite catches all 25, including the four that v0.2.1 missed (M12, M21, M23, M24), each by the check built for it, and M07 now directly (firm first-order condition at the documented δ). This is **not** an independent result: the checks were designed after seeing those misses.
- **Margins.** Every V catch in (ii) exceeds its threshold by a factor of 1e4 or more; in (iii) the smallest factor is 274 (M16, Euler errors at the documented β). The conclusions do not depend on the factor 100 in the threshold rule.

This is a measurement on a second hand-picked sample of 20 errors. It describes this sample only; it is not an estimate of how often either suite catches HANK implementation errors in general (section 10).

## 2. Setup in brief

Full details in the plan, sections 2–8.

- **Suites.** The runner extracts `hank_limits/`, `tests/` and `pytest.ini` of each suite with `git archive` (v0.2.1: `75544da`, trees `ecdf3f3`/`f37e3fa`; v0.3: `96b7fd9`, trees `bd531e6`/`3ff8f32`), so no uncommitted change can enter a run. Mutations go into the copy's `models.py` and `core.py`; the checker side of a suite is never changed.
- **Model side in v0.3.** Only new optional fields in the providers' output (`ss_detail`, `J_A`, `policy`, `drshock`). All 28 v0.1 and 23 v0.2 patches applied unchanged to both suites; no re-anchoring was needed.
- **Detection, time limits, parallelism** as in v0.1: a test catches a mutant when its outcome differs from the same suite's B0; a group catches when any of its tests does; 300 s per fixture or test (never reached); 4 runs in parallel, one BLAS thread each; 67–144 s per run, 24.7 minutes in total.
- **Groups.** T1–T6 and D as in v0.1; V = `tests/test_v0_3_checks.py` (33 tests, v0.3 only). In v0.3, T6 has 7 tests (V5 split). V is reached whenever any of T1–T5 is.
- **Reproducibility.** In both suites B0 and B1 are bit-identical in every summarised number and every outcome. Against `out/mutation_v0_1.json`, all four baselines equal run B0 in all 276 numbers and differ from run B1 only in the known two-valued number (`t5.ssj_inconsistent_options.walras_max.rshock_r_rule`, relative 1.4e-11; plan, section 8).

## 6. Missed errors and why

**Missed by both suites**

- **N20 — constrained share weighted with Dbeg.** A diagnostic only: `mass_at_constraint` feeds `diag['mass_constrained']`, which only T1 asserts (< 1e-5; the value moves from 2.9e-6 to 3.2e-6), and which no V check uses. The model is unchanged.

**Missed by v0.2.1, caught by v0.3**

- **N04 (rate rule on Y_{t−1})** and **N07 (r = 0.005)** leave internally consistent fiscal models: IKC and Walras hold on the solver's own paths, T6's Ricardian bound is looser at r = 0.005, and the F2 pin did not change. Only a check of the documented rule or the documented r can see them.
- **N05 (incidence normalised without e).** T3's zero-liquidity reference is built from the provider's reported ζ and needs only the marginal saver's Euler equation, so the HA response still converges to it. The error is in the specification of incidence (aggregate income ≠ Y to first order), which only V3 checks.
- **N10 (h dropped from the GE options).** Like M12 in v0.1, the T3 outputs move too little for the T3 limit tests; the GE target residual exposes the inconsistency. In T2, T5 and T6 the default step is the step in use, so nothing changes there.
- **N18 (saver target sign).** As for M23 in v0.1, the net-supply error 2 λ A_H vanishes in the limit T2 tests; V2 sees it at the eps where A_H > 0.

**Caught, but missed by groups that execute the code** (v0.2.1 and v0.3 alike)

- N02, N06, N12 (distribution pairing errors) in T1, T3 and T4 (N06 also in T2 and T6, N12 also in T2): β and r recalibrate to the mis-aggregated assets, and T1/T3 references use the reported aggregates; T4's diagnostics use the policy. D caught N02 and N12, whose Dbeg is wrong, but not N06, whose Dbeg is right.
- N08 (asset market against B_{t−1}) in V: the reported asset-market path is not a target, and V2 uses steady-state A and B; only T5's Walras test reads that path.
- N11, N14 (TANK incidence and aggregation) in V: the V2 TANK goods market is computed directly from the type-level C_H, C_S with the documented λ, so a wrong aggregation block does not enter it.
- N03, N09 (cohort simulation) in V: no V test reads the T6 results.

For (iii), the 27 firm group-V predictions all held; M17 (no firm prediction) was caught by the household budget and Aiyagari goods market (7.0e-3, 5.1e-3). The T1–D predictions in (iii) were the v0.1 outcomes, and all held (section 1).

## 8. Controls and false alarms

No control changed any test outcome in either suite: K01 (zero-profit wage), K02 (policy clip removed), K03 (EGM on beginning-of-period assets); in (iii) C01 and C02.

**C03 (T3 GE target goods market instead of bond market) alarms in V1 in the v0.3 suite**, in both `test_v1_werning_ge_target_resid_reported` and `..._direct`: the asset-market residual of the goods-market solve, divided by b, is 3.0e-6 (proportional income) and 2.4e-3 (countercyclical), against a threshold of 2e-12. This was pre-registered (plan, section 7). The cause is F3: SSJ differentiates T3's nonlinear income hetinput one-sided, so the household Jacobians satisfy the aggregate budget identity only to O(h), and the goods-market and asset-market targets are not equivalent at large b (v0.1 report, section 8). It is a true statement about the numerical solution, but it is a false alarm about C03, which is Walras-equivalent in exact arithmetic. The threshold was not adjusted. A suite that wants C03-type changes not to alarm would need F3 fixed upstream, or the T3 provider to differentiate its income itself.

Three controls per suite (six in all) do not make a false-alarm rate.

## 10. Limitations

- **A second hand-picked sample.** The 20 mutants were generated by an agent under a prompt written by the author of the checks, and selected by its order. The agent did not see the tests, the v0.1 report or the plan, but it knew the six categories and the v0.1 list. It is not a random draw from real errors. Detection counts are descriptive of this sample; "the v0.3 suite catches 95% of HANK implementation errors" would be wrong.
- **Many of the gains are specification checks.** N07 and N13 (and M24 in (iii)) are caught because the provider's numbers differ from the documented calibration. Such pins catch any change to a documented value, deliberate or not, and need resetting for another calibration (`spec=`). The household-budget identity and the path checks are model checks that need no documented values.
- **One error at a time**, as in v0.1.
- **"Caught" means an outcome changed**; some catches are errors of a fixture (N19 in T3 and in the V tests on t3).
- **Margins.** The V catches have large margins (section 1). Some old-group catches do not: N15 in the Walras test at 1.17e-7 against 1e-7.
- **One environment.** Python 3.13.16, sequence-jacobian 1.0.0, numpy 2.5.3 (scipy-openblas 0.3.34), scipy 1.18.1, numba 0.68.0, llvmlite 0.50.0, pytest 9.1.1, Linux 6.18 x86_64, 4 CPUs, one thread per run.
- **Unreachable checks.** The F3 pin uses SSJ code only and cannot be reached by model-side mutants; it only signals when SSJ changes.
